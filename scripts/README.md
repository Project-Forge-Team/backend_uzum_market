# scripts/ — сквозная проверка контракта

## e2e.py

55 проверок всего API против **живого** сервера: каталог, фильтры/фасеты,
авторизация (cookie+CSRF), магазин, CRUD товара, отзывы, заказы (включая
недостаток остатка и возврат при отмене), загрузки, demo/reset.

```bash
# локально (сервер уже запущен):
python3 scripts/e2e.py http://127.0.0.1:8000

# после деплоя:
UZUM_BASE_URL=https://<ваш-домен> python3 scripts/e2e.py
```

Только стандартная библиотека — внешних зависимостей нет. Ничего не устанавливает,
в конце сам возвращает БД к сид-состоянию (`POST /api/demo/reset/`).

Особенности:

- Скрипт делает ~8 POST на auth-эндпоинты, а лимит — 10/мин с IP (§4 ТЗ):
  не запускайте чаще раза в минуту (при 429 скрипт сам подождёт и повторит).
- Требует, чтобы сид залит (иначе проверка «categories = 10» не пройдёт):
  `python manage.py seed --reset`.
- Код возврата: `0` — все 55 прошли, `1` — есть падения (удобно в CI).

## seed-products.mjs

Меняет каталог на **живом** сервере: удаляет все текущие товары (активные,
черновики и архив) и публикует 51 товар с реальными фотографиями — данные
лежат в массиве `PRODUCTS` прямо в файле. Работает только через публичное API,
поэтому один и тот же скрипт годится и для прода, и для локального сервера:

```bash
node scripts/seed-products.mjs                  # прод: https://backend-uzum-market.onrender.com
BACKEND_URL=http://127.0.0.1:8000 node scripts/seed-products.mjs
node scripts/seed-products.mjs --dry-run        # ничего не менять, только показать план
```

- Создание/удаление товаров требует сессию продавца, поэтому скрипт логинится
  демо-аккаунтами владельцев магазинов (пароль `Password123`) и работает
  от лица каждого магазина — `seller_id` в данных остаётся за своим магазином.
- Нужен залитый сид (`python manage.py seed --reset`): иначе на сервере не будет
  категорий, магазинов и демо-аккаунтов — скрипт скажет об этом и выйдет.
- Лимиты API соблюдаются паузами (`LOGIN_PAUSE_MS`, `WRITE_PAUSE_MS`):
  логин — 10/мин на IP, запись товаров — 60/час на пользователя.
  На 429 скрипт ждёт `Retry-After` и повторяет запрос.
- Прогон идемпотентен: можно запускать повторно, дублей не будет
  (сначала удаление, потом создание). Полный прогон — ≈3 минуты.
